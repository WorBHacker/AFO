# Архитектура экосистемы AFO

Действующий документ, обновляется с каждым шагом: решения (§4), состояние и известные проблемы (§5), открытые вопросы (§6), этапы и их планы (§7). Журнал работы — `docs/journal.md` (§5.3). Незакрытое — этапами в `docs/problems.md` (D54).

Программа зовётся AFO с 2026-11-04 (Q10, Q18). Папка репозитория `LocalChat`, переменные `LOCALCHAT_*` и пакеты `hub`, `app`, `common` остались прежними.

## 1. Цель и принципы

Не IDE, а **экосистема вокруг общего центра (хаба)**. Хаб постоянно знает проекты, связи между ними, запущенные процессы и вывод терминалов. Чат, VS Code и агенты — это клиенты хаба, которые видят один и тот же контекст. ИИ не нужно каждый раз объяснять, где лежит проект и что в нём происходит.

Принципы:

- **Видеокарта — для моделей, интерфейс — на процессоре.** Qt Quick (QML) с программным рендерером (D3). Без Chromium и WebEngine.
- **VS Code остаётся редактором.** От IDE нужно только дерево папок, просмотр файлов, терминалы и базовый редактор (D47, с 2026-11-02); языковые серверы, отладку и расширения даёт VS Code.
- **Гибрид моделей.** Локальные модели (одна видеокарта, одна модель за раз) + облачные API (параллельно, без ожидания видеокарты).
- **Модель выбирает человек.** Хаб даёт рекомендации с объяснением, но молча модель не меняет.
- **Действия с последствиями — только с подтверждением.** Секреты никогда не уходят в облако.
- **Журналы только дописываются.** История не переписывается.

**Дальняя цель (2026-10-27).** Пользователь хочет в будущем продвигать хаб: им должен пользоваться и человек без технических знаний — поставить программу и ИИ-модели без консоли и ручной настройки (D37, этап 10).

## 3. Компоненты

```
                   ┌──────────────────────── Хаб ─────────────────────────┐
 Приложение ─────▶ │ Проекты и связи · дерево · git · процессы и порты    │ ◀── VS Code / Cline / Roo (MCP)
 (PySide6)         │ Терминалы (ConPTY, хаб — их владелец)                 │ ◀── внешние агенты (Claude Code и др.)
                   │ Инструменты (выполняются локально) · права доступа    │
                   │ Цикл агентов · журнал событий                         │
                   │ Шлюз моделей · рекомендации · учёт расходов           │
                   └──────────┬──────────────────────────┬────────────────┘
                              ▼                          ▼
                 llama-swap 127.0.0.1:8080        Anthropic · OpenAI · Gemini · OpenRouter/DeepSeek
                 (GPU: одна модель за раз)        (параллельно, по API-ключам)
```

- **Хаб** — фоновый процесс на Python. Агенты продолжают работать, когда окно закрыто.
- **Приложение** — нативное окно: проекты с деревом, просмотр файлов, чат, агенты, терминалы, статус модели и памяти.
- **Шлюз моделей** — общий каталог локальных и облачных моделей, адаптеры поставщиков, рекомендации, учёт денег.
- **Внешние агенты** — Claude Code, Codex CLI и т. п. запускаются в терминалах хаба, контекст получают через MCP.
- **VS Code** — редактор. Cline / Roo Code подключаются к хабу через MCP.
- **Автономный агент** (этап 9, D40–D42) — получает цель и сам доводит её до конца: план, шаги, память, проверка себя; действует инструментами хаба и API, инструментами внешних MCP-серверов и — под контролем человека — самим компьютером.

## 4. Принятые решения

**D1. Экосистема с хабом, своё IDE не делаем.** (пересмотрено 2026-11-02: в окне будет базовый редактор — этап 14, D47)
VS Code — редактор. Своё — хаб, лёгкое приложение и агенты.

**D2. Хаб — отдельный процесс.**
Почему: агенты работают без открытого окна; у терминалов один владелец, а смотреть на них могут многие клиенты; внешние клиенты подключаются через MCP.

**D3. Интерфейс: Python + PySide6, Qt Quick (QML) с программным рендерером** (пересмотрено 2026-10-27, было: Qt Widgets).
Интерфейс рисует процессор: Qt Quick включается с программным графом сцены (`QSGRendererInterface.Software`, задаётся до первого окна), видеокарта остаётся моделям. WebEngine — это Chromium, его нет (PySide6-Essentials). Почему не C++: узкое место — модель, а не интерфейс.
Замер (2026-10-26): Electron-программы занимают ~90–110 МиБ видеопамяти каждая (VS Code ~91, Claude ~108, Chrome ~86), NVIDIA Overlay ~123 МиБ.
Замер (2026-10-27, окно 1280×820 на экране, собственная видеопамять процесса): Qt Widgets — 0 МиБ, **Qt Quick с программным рендерером — 0 МиБ (в том числе во время потокового ответа)**, Qt Quick на видеокарте (Direct3D 11) — 24 МиБ. Поверхность окна в DWM считается за самой Windows.
Почему ушли с Widgets: современный вид (свой заголовок окна, всплывающие панели, анимации, сворачивание) на Widgets пришлось бы рисовать вручную по элементу; в QML это встроено. Ограничение программного рендерера: нет шейдерных эффектов (размытие, настоящие тени) — тени рисуются слоями.

**D4. Как хаб видит, что происходит.**

| Источник | Что видно | Как |
|---|---|---|
| Терминалы, запущенные через хаб | весь вывод вживую, команда, код выхода | хаб создаёт их сам (ConPTY) |
| Любые процессы в папках проектов | команда, папка, порты, CPU и память — **без вывода** | psutil |
| Терминалы VS Code | вывод команд | позже: расширение VS Code (shell integration) пересылает в хаб |
| Файлы и git | дерево, изменения, ветка | наблюдение за файлами + git |

**D5. Локальные модели — через llama-swap.**
Один адрес `127.0.0.1:8080/v1`, модель выбирается полем `model`, при смене остальные выгружаются. Состав и замеры — в разделе 5.

**D6. Облачные поставщики:** Anthropic (Claude), OpenAI, Google Gemini (по ключу AI Studio и через Google Cloud Vertex AI — по файлу ключа сервисного аккаунта, этап 30), OpenRouter / DeepSeek и другие OpenAI-совместимые.

**D7. Адаптеры — по поставщику, а не одна OpenAI-совместимая прослойка.**

| Адаптер | Кого обслуживает |
|---|---|
| Anthropic — официальный SDK `anthropic` | Claude по API-ключу |
| OpenAI-совместимый | llama-swap (локальные), OpenAI, OpenRouter, DeepSeek и др. |
| Gemini (REST `generateContent`, без SDK) | Google Gemini по ключу AI Studio; Vertex AI — тот же адаптер со входом по токену OAuth (JWT сервисного аккаунта) и адресом Google Cloud |

Внутри хаба — единый формат сообщений: текст, картинка, вызов инструмента, результат, размышления. Ответ поставщика **хранится как есть**, потому что некоторым поставщикам нужно возвращать собственные блоки без изменений (см. D14).

**D8. Claude Code по подписке — только через официальный CLI `claude`.**

- По документации Anthropic (Agent SDK, 2026-10): сторонним программам без отдельного разрешения запрещено встраивать собственный вход через claude.ai и пользоваться лимитами подписки. Поэтому хаб **не делает свой вход и не трогает токены подписки**.
- Хаб запускает CLI `claude`, уже залогиненный пользователем (так же работает расширение для VS Code):
  - интерактивно — `claude` в терминале хаба;
  - управляемо — `claude -p --output-format stream-json --verbose`; `--resume <session>` продолжает диалог; `--mcp-config` даёт инструменты хаба; `--permission-mode` / `--allowedTools` задают права; `--append-system-prompt` добавляет инструкции.
- Только для личного использования. Если экосистему будут использовать другие люди, им нужны свои API-ключи.
- У подписки свои лимиты использования, они учитываются отдельно от денег по API (D12).
- Заметка: `--bare` подписку **не использует**, ему нужен `ANTHROPIC_API_KEY`.

**D9. Инструменты выполняются локально в хабе — для любой модели.**
Модель только предлагает вызов, хаб выполняет его по правилам доступа. Managed Agents (облачная песочница не видит локальные файлы и терминалы) и облачный MCP-коннектор (нужен публичный адрес) как основу не используем.

**D10. Приватность.**
У каждого проекта флаг «можно отправлять в облако». Секреты (`.env`, ключи, файлы учётных данных) фильтруются всегда, в том числе в результатах инструментов.

**D11. Подбор моделей — гибкий, с рекомендациями.**

- На входе: тип задачи; нужные возможности (инструменты, картинки, контекст); флаг облака у проекта; состояние бюджета и лимитов подписки; что загружено на видеокарте и очередь к ней; **статистика самого хаба** (успешность, скорость и цена за задачу по моделям).
- На выходе: список вариантов с объяснением и оценкой цены и задержки.
- Правила задаёт пользователь: значения по умолчанию для ролей агентов и для проектов, жёсткие ограничения («проект X — только локально»), приоритет между качеством, ценой и скоростью.
- Молча модель не меняется. Автоматика — только если явно включена в профиле.

**D12. Бюджет — гибкий, с рекомендациями.**

- Уровни: общий → поставщик → проект → роль агента → задача. У каждого — мягкий порог (предупредить) и жёсткий (остановить или спросить), плюс период: день, неделя, месяц или задача.
- Учёт по каждому запросу: входные токены, токены из кэша, выходные × таблица цен (в настройках, с датой обновления). Лимиты подписки Claude Code учитываются отдельно. В `claude -p --output-format json` есть `total_cost_usd`, но это оценка на стороне клиента.
- Рекомендации: оценка цены до запуска по похожим задачам, прогноз на месяц, низкая доля попаданий в кэш, избыточная модель для простой задачи.

**D13. Ключи API — в диспетчере учётных данных Windows** (библиотека `keyring`). В файлах настроек ключей нет. Менять ключи и токены — по паролю подключений (решено 2026-10-27 по просьбе пользователя): окно «Подключения» открывается паролем на 10 минут; сам хаб пользуется ключами без пароля (агенты и бот работают без присмотра).

**D14. Журналы только дописываются.**
У новых моделей Claude блоки размышлений нужно передавать обратно без изменений, а правка ранних сообщений их ломает. Сжатие истории — средствами поставщика или новой сессией, но не переписыванием.

**D15. Особенности Claude API, которые учитывает адаптер** (по справке, кэш от 2026-10-06):

- С 2026-10-21 `temperature` / `top_p` / `top_k` вызывают ошибку 400 → адаптер их не отправляет. Глубина регулируется через `output_config.effort`.
- На новых моделях `tool_choice` `any` / `tool` вызывает ошибку 400 → только `auto` + `strict: true` в схеме инструмента.
- `stop_reason: "refusal"` → обработка: запасная модель или сообщение пользователю. Учитывать server-side `fallbacks`.
- Кэширование промпта: в начале — неизменная часть (системный промпт, инструменты, сводка проекта), переменная — после неё.
- Ориентир цен (за 1 млн токенов, вход/выход; чтение из кэша): Opus 5.5 — $4 / $20 (кэш $0.20); Sonnet 5.5 — $2 / $10 (кэш $0.20); Haiku 5.5 — $0.10 / $0.50; Fable 5.1 — $10 / $50. Цены проверять перед использованием.

**D16. Агенты двух видов.**

| | Свои агенты (цикл хаба) | Внешние агенты (Claude Code, Codex CLI…) |
|---|---|---|
| Модель | любая из шлюза: локальная или облачная | своя (Claude Code — по подписке, D8) |
| Инструменты | только инструменты хаба | свои встроенные + инструменты хаба через MCP |
| Права | полностью решает хаб | встроенные — флаги CLI; инструменты хаба — правила хаба (D18) |
| Видимость | каждый шаг | события `stream-json`, а в интерактивном режиме — терминал |

- **Профиль агента:** роль и инструкции, модель с запасной (рекомендации — D11), разрешённые инструменты, режим прав, доступные проекты, бюджет, лимит шагов и времени.
- **Прогон** (задача агента) — журнал, который только дописывается: вызовы модели, вызовы инструментов, подтверждения, расходы. Статусы: в очереди → работает → ждёт подтверждения → пауза → готово / ошибка / отменено. Прогон продолжается после подтверждения или перезапуска хаба. Пока один ждёт подтверждения, остальные работают.
- **Параллельность:** облачные прогоны идут одновременно, локальные стоят в очереди к видеокарте. Планировщик старается не гонять модели туда-обратно.

**D17. Права доступа — по типу действия. Режим по умолчанию «Спрашивать».**

| Тип | Примеры | По умолчанию |
|---|---|---|
| Чтение | файлы, поиск, git status/diff/log, процессы, вывод терминалов | без спроса, в пределах проекта, без секретов |
| Запись | создать или изменить файл | спросить, с показом diff |
| Команды | запуск в терминале | спросить. Команды из белого списка проекта — без спроса |
| Разрушительное | удаление, `git push`, `git reset --hard` | спрашивать всегда, белым списком не разрешается |
| Сеть | запросы, загрузки, установка пакетов | спрашивать каждый раз (D19) |
| Вне проекта или системное | другие папки, настройки Windows | запрещено |

- Режимы: «Только чтение», **«Спрашивать» (по умолчанию)**, «Песочница» (запись в git worktree без спроса, потом просмотр diff), «Доверенный» (без вопроса — правки, команды, сеть и отправка; спрашивается только разрушительное и всё после чтения сайтов, D19 — слово пользователя 2026-10-28; было: белый список + запись в проекте).
- Окно подтверждений: очередь запросов, показ diff или текста команды; «разрешить один раз», «на весь прогон», «всегда для проекта» (создаёт правило), «отклонить с комментарием» (комментарий уходит агенту).
- Перед каждой записью сохраняется снимок файла, поэтому любое действие можно откатить. Полный журнал действий.
- Границы проекта проверяются по нормализованному пути, выйти за папку проекта через символические ссылки нельзя.

**D18. Подтверждения Claude Code — в ту же очередь.**
Claude Code запускается с `--permission-prompt-tool` → инструмент MCP хаба. Его запросы на разрешения появляются в общем окне подтверждений приложения.

**D19. Сеть: спрашивать каждый раз; веб-инструменты есть у всех моделей, в том числе у локальных.**

- Хаб даёт инструменты `web_search` и `web_fetch` (страница → текст) любой модели. У облачного Claude есть и свои серверные веб-инструменты, но для единых правил предпочтительны инструменты хаба.
- Каждый сетевой запрос — с подтверждением. Есть белый список доменов для быстрого разрешения (например, документация, pypi.org, npmjs.com).
- **Содержимое из сети — недоверенные данные.** Инструкции со страниц не выполняются. Агент, который читал сеть, не получает без подтверждения ни запись, ни команды.

**D20. Сначала одна задача — один агент.**
Несколько задач могут идти параллельно. Координатор, который делит задачу на подзадачи для других ролей, сделан в шаге 6.4 (2026-10-27); пачка подзадач с параллельным запуском — D50, этап 16.

**D21. Уведомления о подтверждениях: Windows + Telegram-бот.**

- Windows: всплывающее уведомление и значок в трее, клик открывает окно подтверждений.
- Telegram-бот:
  - отвечает только твоему `chat_id`, кнопки «разрешить» / «отклонить»;
  - токен бота хранится в диспетчере учётных данных;
  - Telegram — облачный сервис, поэтому для проектов **без** флага облака (D10) отправляется только короткое уведомление без кода и diff;
  - разрушительные действия с телефона подтверждаются двумя шагами или не подтверждаются вовсе (Q14).

**D22. Контекст в пять слоёв: давать мало, но нужное. Подробности модель запрашивает инструментами.**

| Слой | Что в нём | Размер | Когда попадает к модели |
|---|---|---|---|
| L0. Карта экосистемы | все проекты (название, назначение одной строкой, стек, статус) + граф связей | ~0.5–2K токенов | всегда, в начале промпта (кэшируется) |
| L1. Карточка проекта | назначение, устройство, ключевые папки, как запускать / тестировать / собирать, соглашения, важные файлы, известные проблемы | ~1–3K на проект | для проекта в фокусе + краткие версии связанных |
| L2. Живое состояние | процессы и терминалы, последние ошибки, изменения git с прошлого сообщения, события | ~0.5–2K, только изменения | в конце промпта, на каждом шаге |
| L3. Подробности по запросу | чтение файлов, поиск, символы, diff, хвост терминала, информация о процессе | порциями | модель вызывает инструменты |
| L4. Память | короткие факты и решения по проектам и связям | ≤ 1K | связанные с проектами в фокусе |

- Порядок в промпте неизменный: L0 → L1 → диалог → L2. Неизменная часть стоит в начале ради кэша промпта.
- Бюджет для модели с контекстом 64K: L0 ≤ 2K; L1 ≤ 3K + по 1K на связанный проект; L4 ≤ 1K; L2 ≤ 2K. Результаты инструментов порциями: файл — 200–400 строк, терминал — последние 100 строк, поиск — 50 совпадений. **Для облачных моделей с контекстом 1M лимиты те же**, потому что каждый шаг агента стоит денег.
- **Инспектор контекста** в приложении показывает, что попало к модели, со счётчиком токенов. Блоки можно выключать, файлы — закреплять.

- Строится на прогонах D16 (вид `autonomous`): те же права D17, подтверждения D38, бюджеты D12, пределы шагов и времени, продолжение после перезапуска хаба.
- Три способа действовать: инструменты хаба и API (Tool-Using), инструменты внешних MCP-серверов (D42), управление компьютером (Computer-Use, D41). «LAM» своей моделью не делаем: это модели с хорошим вызовом функций (выбор — D39) плюс сохранённые удачные последовательности действий — «навыки».
- Память трёх видов: рабочая (заметки прогона; старые шаги — итогом, история не переписывается), долговременная (факты и предпочтения — локально, видны и правятся человеком, Q24), процедурная (навыки).

**D41. Управление компьютером — только под контролем человека.**

- Агент видит экран снимками окна и деревом элементов Windows UI Automation (имена, роли, границы — надёжнее пикселей) и действует щелчками, вводом, клавишами и прокруткой (UI Automation, SendInput).
- Только в программах, разрешённых для задачи; рамка и надпись «Агент управляет компьютером»; глобальная клавиша «стоп» и кнопка в трее; движение мыши человеком — пауза; одна такая задача за раз.
- Никогда сам: поля паролей (UIA IsPassword), ввод учётных и платёжных данных, покупки и переводы, принятие условий — это делает человек. Отправка сообщений и писем — всегда с подтверждением.
- Снимки экрана видит локальная модель со зрением; облачная — только если разрешено (как флаг облака D10, Q20). Каждое действие — в журнале со снимком (срок хранения — D30).

**D43. Каталог программ: что агенту можно, решает человек** (2026-10-27, решение пользователя по Q20).

- Хаб сам находит программы этого компьютера: меню «Пуск» (что человек может запустить, и приложения Microsoft Store), пакеты Store, реестр установленных программ (издатель, версия, папка). Служебные части (библиотеки, обновления, драйверы) в список не попадают; свою программу можно добавить файлом `.exe`.
- У каждой программы — решение: «разрешена» / «запрещена» / «не решено». Не решённая — то же, что запрещённая: агент управляет только разрешёнными (D41). Решает только приложение (токен `app`), не агент и не клиент MCP.

Найденная после первого обзора программа — всплывающее окно «разрешить / запретить / решить позже» (и уведомление Windows, если окно позади). Первый обзор не засыпает вопросами: одно предложение «найдено N программ — выбрать, что можно».
- Удалённая программа помнит своё решение: поставят снова — решение то же.

**D44. Режим «Цель»: работа до результата, а не до конца ответа** (2026-10-28, решение пользователя: в чате и в «Агенте»; подробный план пользователя — `docs/goal_engine.md`, по образцу `/goal` у Codex и Claude Code).

- В обычном чате и в сеансе проекта человек ставит цель: что должно стать правдой в конце («тесты проходят», «в `count.txt` — число строк»). Модель работает ход за ходом с правами этого чата (D17, чип прав), подтверждения приходят обычной карточкой (D38). Цель ставится, ставится на паузу, продолжается и снимается из поля чата. Поле во время работы открыто: написанное туда — уточнение, модель прочтёт его в начале следующего хода, не прерывая текущий.
- Три части, и закрыть цель может только одна:
  - **исполнитель** — модель чата со своими инструментами; делает работу, но объявить цель достигнутой не может;
  - **оркестратор** — код хаба, не модель: после каждого хода считает пределы, запускает проверки, ставит точки сохранения и выбирает путь;
  - **проверяющий** — только читает: сначала проверки без модели, потом лёгкая модель-судья (Q26).
- Цель — договор, он хранится отдельно от разговора: что нужно; критерии готовности (команда с ожидаемым кодом выхода или смысловое правило); жёсткие ограничения; этапы; пределы (по умолчанию 25 ходов, 500 тыс. токенов, 60 минут, на 88 % — мягкая остановка); счётчики; очередь уточнений. Договор по словам человека составляет лёгкая модель («компилятор цели»: измеримый критерий вместо «оптимизируй запросы»), человек утверждает его карточкой (D38) — «Подтвердить и запустить». Команды критериев утверждаются вместе с договором.
- После каждого хода — один из четырёх путей:
  - **дальше** — цель не достигнута, пределы в норме: сообщение хаба с целью, этапом, вердиктом проверяющего и уточнениями человека, затем новый ход;
  - **достигнута** — все критерии проверены: итог с изменениями, временем и результатами проверок;
  - **стоп для человека** — попытка нарушить ограничение или зацикливание: пауза, уведомление Windows и Telegram (D21) с вариантами;
  - **предел** — израсходовано 88 %: последний ход, чтобы привести файлы в рабочее состояние и написать, что готово, где остановился и что осталось.
- Проверка в два контура. Сначала без модели: команды критериев и синтаксис изменённых файлов (tree-sitter). Если что-то упало, модель-судья не вызывается, исполнитель сразу получает вывод. Если всё чисто, модель-судья сравнивает договор с фактом (diff, вывод команд) и словам исполнителя не верит. Ответ — `ACHIEVED` / `INCOMPLETE` / `REGRESSED`; удалённый, закомментированный или пропущенный тест — `REGRESSED`.
- Защита от зацикливания. Отпечаток ошибки — sha256 вывода упавшей команды без времени, временных путей и адресов. Сигналы: одна и та же ошибка 3 хода подряд; чередование A→B→A→B; один файл правится больше 4 раз за этап, а падений не меньше. Тогда сначала ход «следователя» (только чтение, найти причину), потом — стоп для человека.
- Этапы. Проверенный этап становится точкой сохранения: невидимая ссылка git `refs/localchat/goals/<цель>/<этап>`, не в истории веток. В запросе его вызовы инструментов заменяет одна строка итога. В тупике — откат к последней точке и указание идти другим путём.
- Смена моделей по ходу: сильная — на план и трудные места, дешёвая — на обычные шаги.
- Как план пользователя поправлен под прежние решения:
  - журнал не переписывается (D14): итог этапа заменяет вызовы только в запросе (как `hub/fit.py`). Сообщения хаба между ходами хранятся и видны (в окне — свёрнутой строкой), а не скрыты;
  - список инструментов разговора не меняется (D14, размышления Claude): «следователь» не отключает инструменты — хаб на этот ход отклоняет вызовы записи и команд (как «сначала план» в 9.1);
  - откат файлов без вопроса — только в «Песочнице», где файлы — копия агента. В проекте — карточкой «вернуть к точке …»: человек мог править рядом (D17);
  - смена моделей — только если человек включил её в договоре; каждая смена видна в ленте (D11), облачная модель — только там, где проекты разрешают облако (D10);
  - проверяющий — своя роль «Проверка цели» (D39, шаг 8.4). Облачная модель видит diff только проектов с облаком и только после фильтра секретов (D10); её расход учитывается (D12);
  - хаб не угадывает линтеры и тесты проекта: запускаются только команды из договора и проверка синтаксиса;
  - в чатах с Claude Code исполнитель — CLI: ходы продолжает хаб, а «следователь» — это отказ на запрос прав (`--permission-prompt-tool`).
- Цель продолжается после перезапуска хаба (D16). Проверки только дописываются в журнал (D14), их расход учитывается (D12).
- В «Агенте» отчёт `finish` с «цель достигнута» перепроверяет тот же проверяющий, а не сам агент. При несогласии агент узнаёт, чего не хватает.

**D45. Полигон и экзамен моделей** (2026-10-30, слово пользователя: «сделай песочницу для примеров и для задач и жёсткие экзамены между большими [моделями]»).

- **Полигон** — набор готовых заданий внутри программы. Каждое — маленький учебный проект и договор цели (D44): что сделать, критерии-команды, ограничения, пределы. «Попробовать» с выбранной моделью делает свежую копию учебного проекта в папке данных (`data/proving/<прогон>`, git-репозиторий с первым коммитом) и чат с режимом «Цель» на ней. Человек смотрит, как модель работает, и может вмешаться, как в любом чате с целью.
- Копия — песочница модели: права «Доверенный», писать и запускать там можно без вопросов. То, что всё равно спрашивается (разрушительное, сеть, вопрос модели человеку), на полигоне не ждёт человека, а получает отказ: «на полигоне некому ответить — решай сам». Учебные проекты и чаты полигона не попадают ни в список проектов, ни в карту проектов других чатов (D27), ни в список чатов; открываются из полигона.
- **Экзамен** — выбранные задания на выбранных моделях, по очереди (локальные модели всё равно делят одну видеокарту). Каждый прогон — на своей свежей копии. «Жёсткий»:
  - цель закрывается только проверками хаба (D44: команды, синтаксис, потерянные тесты; судья — по выбору экзамена);
  - после цели хаб запускает **скрытые проверки** задания — модель их не видит, они лежат в программе, а не в копии. Сдано = цель достигнута **и** все скрытые проверки прошли;
  - пределы задания одинаковы для всех моделей; время на прогон ограничено жёстко.
- Итог экзамена — таблица «задания × модели»: сдано или нет и почему, ходы, токены, время, цена; по каждой модели — сколько сдано и сколько стоило. Экзамены хранятся (D14), их можно сравнивать и удалить вместе с копиями.
- Задания используют интерпретатор Python самой программы (в договоре — подстановка `{python}`), чтобы не зависеть от того, что установлено у человека.

**D48. Два языка: русский и английский** (2026-11-04, слово пользователя: «переводи интерфейс на английском и добавь переключение»).

- **Источник — русский текст в коде.** Он же ключ каталога (`common/locale/en.json`: русский текст → английский), как msgid у gettext. Русский вывод не меняется ни на знак, сотни тестов его сверяют; кода, где английский — источник, нет.
- **Разметка.** Python: `tr("Удалить «{name}»?", name=x)` — перевод, затем поля (`str.format`); `plural(n, "файл", "файла", "файлов")` — английский берёт из каталога две формы (`"file|files"`); константы, которые считаются при импорте, — `N_()`, перевод там, где текст показан. QML: `qsTr("…")`, значения — `.arg()`; Qt спрашивает переводчик AFO (`app/ui/translator.py`), тот отвечает из того же каталога. Журналы, докстроки и то, что уходит моделям, не переводятся; русское, что должно остаться русским (образцы русского ввода, названия языков на своём языке), помечается `i18n: keep`.
- **Проверка** (`tests/test_i18n.py`, `python -m common.i18n_catalog`): в каталоге есть каждый размеченный текст и нет лишних, поля и `%1` сохранены, формы множественного числа — две, русских букв в переводе нет; в переведённых файлах не осталось неразмеченного русского текста.
- **Какой язык.** `LOCALCHAT_LANGUAGE` → выбор человека в «Настройках» (окно хранит его в `app.ini`, хаб — копию в своей базе) → язык, на котором шёл установщик (`HKCU\Software\AFO\Language`) → первый из предпочитаемых языков Windows, который AFO знает → английский. Существующие установки на русской Windows остаются русскими.
- **Переключение — окно открывается заново.** Тексты окна делаются при его запуске (Python-строки моделей и списков), поэтому другой язык — новый процесс окна, старый закрывается; хаб, его чаты и агенты работают дальше (D2). Хаб узнаёт язык сразу (`PUT /v1/language`) и при каждом подключении окна; то, что хаб пишет людям (ошибки, проверки, уведомления, Telegram), — на нём. Уже сохранённые тексты (история, лента) остаются на языке, на котором были написаны.
- **Одно русское слово — два смысла.** «Свернуть» у кнопки окна — Minimize, у карточки — Collapse: такой текст в QML размечается с уточнением, `qsTr("Свернуть", "window")`, и в каталоге у него свой ключ (`window\x04Свернуть`, как msgctxt у gettext).
- **Числа.** Десятичный разделитель — по языку (`i18n.decimal`): «1,5 ГБ» по-русски, 1.5 GB по-английски.
- **Расширение VS Code** — по языку самого VS Code, его способом (`vscode.l10n.t`, `package.nls.*.json`): там источник — английский, русский — в `l10n/bundle.l10n.ru.json`; так требует VS Code.
- **Что остаётся русским в хабе** (`# i18n: keep`): тексты для моделей (подсказки и инструкции агенту, заметки в контексте, карточка проекта, файлы для других инструментов, задача цели), образцы русского ввода (`[д/н]`, адреса), имена и значения, которые хранятся и сравниваются (профиль «Автономный агент», уровни заданий), справочник `docs/API.md`. Задания полигона: людям — название, уровень, описание и пояснения к проверкам на языке окна (`"en"` в `task.json`), а сама задача модели (`objective`, `constraints`) — одна на все языки, чтобы экзамены сравнивались; материалы экзаменов (`proving_tasks/*/files`) проверка разметки не читает.
- **Заголовок раздела — на двух языках** («Язык · Language»): кто не читает текущий язык окна, найдёт переключатель.

**D49. Модели, что уже лежат на дисках, и параметры запуска по замерам** (2026-11-04, слово пользователя: «ещё нужно сделать поиск модели внутри дисков и полная автоматическая оптимизация»; ответы на его вопросы — тем же днём, все четыре — рекомендованные).

- **Где искать** — все локальные диски целиком, в фоне; системные папки (Windows, Program Files, корзина, «System Volume Information») и ссылки на другие папки пропускаются. Ищутся файлы GGUF от 50 МБ (меньше — словари и тестовые), части одной модели (`-00001-of-00003.gguf`) — одна модель, проектор картинок (`mmproj`) — к модели из той же папки; модели Ollama — по его манифестам (их файлы без расширения).
- **Найденное — список, добавление по кнопке.** Имя, размер, сжатие, поместится ли в видеопамять; «уже в конфиге», если llama-swap уже ссылается на файл. «Добавить» пишет модель в конфиг llama-swap прямо с того места, где лежит файл, без копирования — тем же путём, что установка с Hugging Face: план запуска, пробный запуск. «Удалить» такую модель убирает только её запись из конфига: файл — человека, AFO его не трогает.
- **Оптимизация — параметры запуска моделей** по замерам на этом компьютере: слои на видеокарте, контекст, flash attention, сжатие KV-кэша, потоки, batch, вынос экспертов MoE на процессор. Лучшее — в конфиг llama-swap, прежний — копией рядом. Выбор моделей под задачи — не сюда.
- **Когда** — сама: после установки или добавления модели и после обновления llama.cpp, когда модель не занята; и по кнопке «Оптимизировать» у модели. Для замера модель загружается и занимает видеопамять — несколько минут на модель.

**D50. Координатор и исполнители (Orchestrator-Workers)** (2026-11-05, план пользователя из пяти узлов; «Начни» — тем же днём). Развивает D20: координатор раздаёт подзадачи пачкой, а не по одной.

- **Пачка с зависимостями** — инструмент `delegate_tasks`: до 8 подзадач (`task_id`, `agent_profile`, `prompt`, `dependencies`); хаб проверяет всё до запуска (агенты есть, имена задач уникальны, зависимости — внутри пачки и без циклов). Независимые идут сразу, зависимая — когда закончились те, от кого она зависит, и получает их ответы; не удалась зависимость — задача пропускается с причиной. Координатор ждёт всех и получает компактную доску (статус и ответ каждой), а не переписку исполнителей. `delegate_task` остаётся.
- **Облако и видеокарта**: облачные подзадачи — одновременно (не больше 4 сразу на пачку); локальные — через ту же очередь к видеокарте, что у всех прогонов (семафор на весь прогон, D16), в пачке — подряд по модели, чтобы llama-swap не перегружал модели туда-обратно. Пока координатор ждёт, видеокарта не его.
- **Файлы** — у каждого пишущего исполнителя своя песочница (D17: worktree в папке данных, не рядом с проектом); зависимая задача начинается с результата той, от которой зависит. В проект изменения попадают только по кнопке пользователя, как в «Песочнице»: хаб не коммитит и не сливает ветки в проекты пользователя.
- **Проверка исполнителя** — у задачи могут быть критерии; результат проверяет судья режима «Цель» (D44: сначала без модели, потом модель-судья), до 3 кругов; координатор получает только принятое с diff или «нужен человек» (ESCALATION) со словами судьи.
- **Доска** — подзадачи в базе (таблица, а не текст беседы): в окне у прогона координатора — таблица статусов; подтверждения исполнителей — под ним. Один уровень, как в D20: исполнитель дальше не поручает; Claude Code исполнителем не бывает (профили агентов его не принимают).

**D51. Выборочное применение правок** (2026-11-05, разбор пользователя «поханкового применения»: с чего начать — с файлов песочницы; «начинай» — тем же днём).

- Карточка подтверждения и песочница принимали правку модели целиком. Теперь человек выбирает: в песочнице — файлы (17.1), на карточке подтверждения — ханки (17.2–17.3); по желанию — ханки и в песочнице (17.4).
- **Песочница.** Невыбранное остаётся в ней, а её база сдвигается на служебный коммит хаба «база + перенесённые файлы» под своей ссылкой `refs/localchat/sandbox/<чат>`: дальше diff показывает только то, что ещё не перенесено. В ветки пользователя хаб по-прежнему не коммитит.
- **Ханки.** Файл собирается заново по операциям `difflib` (в выбранных ханках — строки «после», в остальных — «до»), без пересчёта смещений и без `git apply`; концы строк и BOM — как у файла. Модель получает список отклонённого (строки и имя функции по индексу символов), а запись поверх файла без нового чтения ей запрещена: хаб не считает, что она знает итог (`seen` не обновляется).

**D52. Поиск по смыслу без векторов** (2026-11-05, разбор пользователя: подбор слов, полнотекстовый индекс по определениям, механизмы в карточке; «начни» — тем же днём). Развивает D26: всё на процессоре, без эмбеддингов.

- **Несколько слов кода сразу.** Идею («где проверка прав?») модель ищет одним `search_code` по нескольким словам, какими их пишет код, — по-английски, регулярным выражением (`permission|authoriz|forbidden`); об этом говорят описание инструмента (полное и короткое) и ответ «ничего не найдено» (18.1).
- **Механизмы в карточке.** Раздел «Ключевые механизмы и где они»; черновик пишется по настоящим определениям главных файлов из индекса символов, а не догадкой по дереву папок (18.2).
- **Полнотекстовый индекс по определениям** (SQLite FTS5, стемминг): имя, разобранное на слова, владелец, путь, первая строка, docstring и комментарий над ним. `find_symbol` с несколькими словами ищет по нему (BM25), с одним — по имени, как раньше: отдельного инструмента нет, потому что каждое лишнее описание стоит токенов в каждом запросе. Какие поля брать — по замеру на коде самой AFO (16 вопросов с известным ответом, `tests/stress/test_meaning.py`): нашёл 15, из них 11 — первой строкой; `search_code` с теми же словами регулярным выражением — 0–1 (общие слова забивают его 50 строк) (18.3).

**D55. Картинки и видео на любом компьютере** (2026-11-06, идея пользователя «Визуальный модуль: создание картинок и видео без мощного железа» и его слово «вылизывать план и архитектуру, проверить максимальную совместимость для слабых ПК и ноутбуков, найти решение в интернете и на форумах, переделать план»; «Начни разработку визуального модуля» — 2026-11-07). План, исследования и источники — `docs/visual.md`.

- **Один движок** — stable-diffusion.cpp (`sd-server`, MIT, без PyTorch): картинки и видео на всех уровнях, запуск через llama-swap, как модели чата. Ставится закреплённая проверенная сборка, а не самая новая: выпуски идут по нескольку в день, и среди них бывают сломанные.
- **Картинки — на любом компьютере**, даже без видеокарты; **видео локально — от NVIDIA 6 ГБ и 16 ГБ ОЗУ**, на 4 ГБ — «попробовать медленно», ниже — облако (по замеру 29.1; план говорил 8 ГБ и 32 ГБ — по отчётам о моделях 14B). Уровень компьютера решают пробный запуск и замер на нём самом (как параметры моделей чата, D49), а не таблица: слабое железо ломается на краях — предел одного блока памяти Vulkan, бюджет памяти движка, не равный всей памяти карты.
- **Сбой — ступенью ниже, без вопроса**: раскладку весов по памяти и повтор VAE кусками делает сам движок (29.1); дальше AFO — меньший размер → модель ступенью ниже → сборка для процессора → карточка облака с ценой. Сбой — код выхода не 0 или пустая картинка; `out of memory` в журнале при нормальном итоге — не сбой. Пустую серую картинку с «успехом» хаб распознаёт сам. Ступень, на которой вышло, запоминается для модели и компьютера.

- **Облако — не тихо** (D10–D12): карточка с ценой и причиной; разрешение заранее с потолком в день — настройкой; проект с запретом облака туда не уходит никогда. Видеокарта одна: локальное задание — в общей очереди с агентами (D16).

**D56. Режим «Полный»: агент ничего не спрашивает** (2026-11-08, слово пользователя по задаче «отвечать в Telegram тем, кто пишет мне»: «нужно добавить полный автоматизированный режим в котором агент не должен спросить о разрешение даже когда оно пишет или что-то делает. и нужно исправить саму режим авто»). Развивает Q22 и D40, меняет D41 («отправка — всегда с подтверждением») и D43 для этого режима. Этап 33, `docs/problems.md`.

- Четвёртый уровень автономной задачи — **«Полный»** (`full`), над «Авто»: план не утверждается, и ни одной карточки — запись в проекты, команды, сеть, отправка сообщений и писем, личные факты в память, программы. Каждое такое действие всё равно в журнале подтверждений — разрешено уровнем (`decided_by = full`).
- **Чего «Полный» не делает вовсе** — выбор пользователя 2026-11-08 («Не делать их», а не «спрашивать» и не «делать»): удаляющее и необратимое (git push, rm -r, диски, реестр; команда, которая запускает не названное в своей строке), команды, достающие данные хаба (ключи, базу), запись поверх несохранённого в редакторе окна. Агенту — отказ без вопроса, в отчёте — что не сделано. Как и в любом режиме, никогда: пароли, оплата, переводы, принятие условий (D41); окно AFO с рамкой и «Стоп» открыто; ввод человека — пауза; пределы шагов, времени и денег; условия «готово».
- **Программы** («Полный»): любая программа этого компьютера, которую человек не запретил в «Программы для агента», — без разрешения заранее. В остальных режимах программу, которой нет среди разрешённых, хаб спрашивает сам, один раз, карточкой с кнопками; «Разрешить» записывает решение туда же, где его ставит человек (D43), — словами в ответе агенту программа не разрешается.
- Модели сказано: не спрашивать разрешения и подтверждения — хаб сам спросит, где нужно.

**D57. Пробный запуск — по кнопке и по одному; видеокарта — одна очередь** (2026-11-08, слово пользователя по «Установке моделей → На этом компьютере»: «когда я добавляю модели они сразу начинают процесс пробного запуска это неправильно ведь я могу что-то делать во время этого … пробный запуск шёл по тем кого первым я добавил по порядку … из-за этого память переполнилась»; решения этапа доверены Claude — «принимаю твои решение»). Меняет D49 («Добавить» — сразу пробный запуск; подбор параметров — сам после добавления). Этап 34, `docs/problems.md`.

- **«Добавить»** модель с дисков только записывает её в конфиг llama-swap: «добавлена, не проверена». Ничего не загружается и не замеряется.
- **«Пробный запуск»** — кнопкой рядом с «Добавить файл…» (все непроверенные) или у модели в «Установках»: по одной, в том порядке, в каком их добавляли; перед каждой — пока чат не закончит отвечать. Модель с Hugging Face, как прежде, проверяется сразу после загрузки (выбор Claude, можно поменять).
- **Видеокарта — одна очередь.** Пробный запуск и замер «Подбора параметров» (llama-bench идёт мимо llama-swap) не идут одновременно: автоматический подбор ждёт, пока у установок есть дело, и уступает начатой проверке, как уступает чату.
- **Конфиг llama-swap** меняется по одному: прочитан, изменён и записан под одной блокировкой хаба; «Подбор параметров» правит файл таким, каким он стал к концу замера, и откатывает только свою модель.

Команды, которые Claude Code сам считает безопасными (`Write-Output`), он выполняет, не спрашивая хаб, — правило 13.12 «команда, упоминающая папку данных хаба, спрашивается и в «Доверенном»» видит только то, что он спросил. Файлы вне своей рабочей папки Claude Code и сам не читает (`Get-Content` отклонил), а команда, которой нужно разрешение (`python -c` с чтением), пришла карточкой. Принято (25.5): пометка «С ошибками» в её настройке — и хаб не советует её для чатов и не берёт для карточек, пока есть другая.
- Стенд (2026-11-06, при шаге 26.2, на этой машине) — два мягких предела превышены и без шага:
  - шторм из 5000 изменений даёт 11–12 событий `project.files` при пределе 10;

  Предел не поднят: это замер, его смотрят на чистой машине.

У настоящих проектов это обычно закрывает их `.gitignore`; общий фильтр мусора, как у истории файлов вне git, — по отдельному слову.
- Окно: смена темы в чате из 1000 сообщений держит поток окна ~0,66 с — все строки строятся заново (замер 13.7). Действие редкое, не трогали. Терминал в окне: быстрая отрисовка — только для символов шириной в одну клетку; поток иероглифов или комбинируемых знаков рисует pyte, в 2–3 раза медленнее.

- 14.2 — окно, редактор одного файла. Шаг большой и первый в окне, поэтому идёт тремя коммитами, как 13.3: 14.2а — редактор: правка, Ctrl+S, отступы, полоса «файл изменился на диске», строка состояния (сделано 2026-11-03, см. журнал); 14.2б — подсветка: экран и строки вокруг него, кусками, дальше — когда до них дойдёт экран (сделано 2026-11-03, см. журнал); 14.2в — несохранённые правки известны хабу, запись модели в такой файл спрашивается в любом режиме (сделано 2026-11-03, см. журнал):
  - `CodeEditor.qml` — `TextEdit` в `Flickable`, номера строк только для видимых строк, подсветка текущей строки;
  - `app/ui/editor.py` — буфер, «не сохранено», сохранение, перечитывание;
  - `app/ui/highlighter.py` — подсветка. Как сделано (14.2б, по замерам; план разбора 13.15 изменён там, где замер его опроверг): Pygments разбирает весь текст в фоне через 150 мс после последней клавиши, цвета из `app/palette.py`; поток окна накладывает их только на строки, до которых достаёт экран, — сам экран и по 200 строк вокруг, кусками; остальные — когда до них дойдёт экран. Строка, в которой печатают, красится сразу сама по себе. Почему не «перелексировать с изменённой строки»: многие лексеры Pygments ловят многострочный комментарий или строку одним выражением, построчно они красят неверно. Почему не «остальное кусками по 8 мс»: наложение цвета стирает раскладку строки, а любая следующая пометка пересчитывает раскладку от себя до конца файла — раскрашенное заранее вне экрана стоило 0,4 с на первой же пометке перед ним. tree-sitter для подсветки не взят: Pygments уже есть у просмотрщика для всех языков; символы буфера (14.5) — отдельный вопрос;
  - клавиши: Ctrl+S; отмена и повтор (Ctrl+Z, Ctrl+Y); Enter сохраняет отступ строки и добавляет его после `:` или `{`; Tab и Shift+Tab — отступ, в том числе у выделенных строк. Единица отступа — как в файле;
  - полоса «файл изменился на диске»: «Взять с диска», «Сравнить», «Оставить мой». Если правок нет, файл перечитывается сам, место курсора и прокрутки сохраняется;
  - внизу — кодировка и концы строк; невидимые символы помечены (13.5);
  - файл больше предела или бинарный открывается в нынешнем просмотрщике;
  - несохранённые правки и запись модели (разбор 13.15). Одного предупреждения на карточке мало: в «Доверенном» карточки нет, и модель записала бы файл под несохранённым буфером. Окно сообщает хабу, какие файлы открыты с правками (проект и путь — sha256 основы для вопроса не понадобился; `PUT /v1/editor/dirty`, только окно; хаб забывает их через 30 с после того, как у него не осталось ни одного соединения событий окна). Запись модели в такой файл — `write_file`, `edit_file`, `Edit`/`Write` Claude Code через `approval_prompt` — спрашивается в любом режиме, «Доверенный» тоже, с предупреждением «файл открыт с несохранёнными правками» на карточке; в «Песочнице» запись идёт в worktree, вопрос не нужен. ### План этапа 19 — стыки «Цели», песочницы и поиска (D53; записан 2026-11-06 по общему тесту; сделан 2026-11-06)

Порядок — от самого опасного. У каждого шага уже есть тест в `tests/test_together.py` (сейчас `xfail`); шаг снимает пометку.

- 19.1 (сделано 2026-11-06, см. журнал) — этапы и защита от хождения по кругу (11.5 × 11.4). У цели, чей критерий выполняется только в конце («тесты проходят»), проверка после каждого этапа падает одинаково — отпечаток тот же. Защита считает это повтором: на втором ходу шлёт «следователя» (запись и команды отклоняются), на третьем останавливает цель — хотя каждый ход закрыл этап. Решение: принятый этап — прогресс; сигналы считаются заново с него, как после паузы или отката. Тест `test_stages_that_go_on_are_not_going_round_in_circles`.
- 19.2 (сделано 2026-11-06, см. журнал) — «Применить всё» посреди цели (17.1 × 11). Применение последнего файла убирает песочницу; цель продолжается в новой — от последнего коммита, без того, что человек только что перенёс в проект (оно там не закоммичено): выполненный критерий снова падает, и цель встаёт. Решение: новая песочница чата с открытой целью начинается от базы прежней (`refs/localchat/sandbox/<чат>`: «коммит + перенесённое»), а не от `HEAD` — или песочница с открытой целью не убирается. Тест `test_a_goal_goes_on_with_what_the_user_applied`.
- 19.3 (сделано 2026-11-06, см. журнал) — откат после частичного применения (17.1 × 11.6). Откат песочницы к точке сохранения возвращает и то, что человек уже перенёс в проект: песочница показывает перенесённый файл «удалён», и «Применить всё» удалило бы его из проекта. Решение: файлы, перенесённые после точки, откат берёт из базы песочницы, а не из точки. Тест `test_a_dead_end_after_a_part_was_applied_does_not_take_it_back`.
- 19.4 (сделано 2026-11-06, см. журнал) — индекс символов песочницы (9.4б × 18.3). Откат удаляет или возвращает файл, открытый в редакторе окна с несохранёнными правками, а карточка об этом молчит; у правки модели такая пометка есть. Решение: пометка `unsaved` — по файлам отката.
