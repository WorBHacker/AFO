# Архитектурный регламент и спецификация внедрения системы Goal Engine

Данный документ представляет собой инженерную спецификацию (RFC) для разработки и внедрения автономного целеполагающего цикла (**Goal Mode / Goal Engine**) по образцу агентной архитектуры OpenAI Codex и ChatGPT.

---

## 1. Концептуальная архитектура и разделение ролей

Классический чат-интерфейс работает по схеме реактивного цикла: **Пользователь $\rightarrow$ Модель $\rightarrow$ Пользователь**.  
Режим **Goal Engine** переводит систему в замкнутый автономный контур управления с обратной связью (*Closed-Loop Control System*), где управление возвращается человеку только при достижении цели, исчерпании бюджета или возникновении критического блокера.

### Три изолированных компонента системы

Чтобы исключить проблему «галлюцинации успеха» (когда агент устает от контекста, удаляет падающий тест и отчитывается о готовности), система разделяется на три независимых узла:

1. **Worker Agent (Агент-исполнитель):**
   * Основная LLM с доступом к инструментам (`bash`, `file_edit`, `web_search`, `mcp_tools`).
   * Решает атомарные задачи в рамках текущего этапа (`milestone`).
   * Не имеет права самостоятельно закрыть глобальную цель (`Goal`).
2. **Loop Orchestrator (Детерминированный контроллер цикла):**
   * Программный модуль на стороне бекенда или локального рантайма (не LLM!).
   * Перехватывает завершение хода Исполнителя, считает бюджеты (токены, шаги, время), проверяет инварианты безопасности, управляет чекпоинтами Git и маршрутизирует выполнение.
3. **Evaluator / Judge (Ревизор верификации):**
   * Двухконтурный модуль проверки (детерминированные скрипты + легкая LLM-судья).
   * Не имеет инструментов записи или модификации файлов (режим `read-only`).
   * Сверяет фактическое состояние среды (диффы, коды возврата тестов, логи сборки) со списком `completion_criteria` и выносит вердикт: `ACHIEVED`, `INCOMPLETE` или `REGRESSED`.

## 3. Жизненный цикл и 4-путевая маршрутизация (4-Path Loop Routing)

Когда `Worker Agent` завершает генерацию очередного ответа (перестает вызывать инструменты и выдает текстовое резюме шага), управление перехватывает `Loop Orchestrator`.

```
[Ход Worker Agent завершен]
            |
            v
[Контур 1: Детерминированные проверки (AST, Linters, Tests)]
            |
            v
[Контур 2: Оценка LLM-Ревизором + Проверка бюджетов и ошибок]
            |
            +---> 1. Все критерии = TRUE ---------> [ПУТЬ Б: ACHIEVED (Успешный выход)]
            |
            +---> 2. Опасная операция / Зацикливание -> [ПУТЬ В: BLOCKED (Пауза + Запрос человеку)]
            |
            +---> 3. Бюджет >= 88% (Soft Limit) ----> [ПУТЬ Г: BUDGET_LIMIT (Финализация и парковка)]
            |
            +---> 4. Цель не полная + Бюджет ОК ---> [ПУТЬ А: CONTINUE (Скрытый авто-ход)]
```

### Детализация маршрутов

1. **Путь А (`CONTINUE` — Автоматическое продолжение):**
   * **Условие:** Цель еще не выполнена, лимиты в норме, зацикливания нет.
   * **Действие:** Оркестратор забирает сообщения из очереди `steering_queue` (если пользователь что-то дописал на ходу), добавляет вердикт Ревизора и отправляет скрытый системный промпт продолжения.
2. **Путь Б (`ACHIEVED` — Завершение цели):**
   * **Условие:** Все автоматические проверки и `completion_criteria` имеют статус `verified = true`.
   * **Действие:** Оркестратор закрывает цикл, формирует финальный отчет (дифф изменений, время работы, результаты тестов) и переводит UI в режим ожидания новой задачи.
3. **Путь В (`BLOCKED / ESCALATE` — Предохранитель):**
   * **Условие:** Агент пытается нарушить `hard_constraints`, требует прав на деструктивное действие или сработал детектор зацикливания ($\ge 3$ одинаковых ошибок подряд).
   * **Действие:** Выполнение ставится на паузу (`paused_for_human`), пользователю отправляется уведомление с описанием блокера и вариантами решения.
4. **Путь Г (`BUDGET_LIMIT_REACHED` — Мягкая парковка):**
   * **Условие:** Израсходовано $\ge 88\%$ лимита ходов, токенов или времени.
   * **Действие:** Оркестратор инжектирует специальный промпт завершения бюджета, требующий от агента немедленно прекратить начатые эксперименты, привести код в рабочее состояние и записать подробный план оставшихся работ для следующей сессии.

Ниже приведены шаблоны скрытых сообщений, которые Оркестратор автоматически подставляет в цикл.

### 4.1. Промпт автоматического продолжения (`Continuation Prompt`)
```xml
<system_loop_directive type="continuation">
Работа над глобальной целью продолжается. НЕ пиши вводных приветствий и отчетов для пользователя — сразу переходи к вызову инструментов.

[ТЕКУЩАЯ ЦЕЛЬ]: {{contract.objective}}
[АКТИВНЫЙ ЭТАП]: {{current_milestone.title}}

[ВЕРДИКТ РЕВИЗОРА ПО ПРОШЛОМУ ХОДУ]:
Статус: НЕ ЗАВЕРШЕНО.
Причина: {{evaluator.missing_requirements}}
Лог последней ошибки: {{evaluator.last_error_snippet}}

{{#if steering_messages}}
[КОРРЕКТИРОВКА ОТ ПОЛЬЗОВАТЕЛЯ НА ЛЕТУ]:
{{steering_messages}}
Учти это требование как приоритетное на текущем шаге!
{{/if}}

Выполни следующий шаг для закрытия активного этапа.
</system_loop_directive>
```

### 4.2. Промпт исчерпания бюджета (`Budget Limit Prompt`)
```xml
<system_loop_directive type="budget_limit_warning">
ВНИМАНИЕ: Исчерпан лимит ресурсов текущей сессии (ход {{telemetry.turns_used}} из {{budget.max_turns}}). 
У тебя остался ПОСЛЕДНИЙ ход перед автоматической остановкой цикла.

Твои обязательные действия прямо сейчас:
1. НЕ начинай новых рефакторингов и не создавай новых модулей.
2. Убедись, что все измененные файлы сохранены в синтаксически корректном состоянии (без оборванных блоков кода).
3. Сформируй финальную сводку (Handover Report):
   - Что уже полностью готово и проверено.
   - На каком конкретном файле и строке остановилась работа.
   - Какие шаги нужно выполнить при перезапуске цели.
</system_loop_directive>
```

### 4.3. Промпт для модели-Ревизора (`Evaluator / Judge Prompt`)
```xml
<evaluator_instructions>
Ты — независимый аудитор выполнения задачи (Judge). У тебя нет прав на редактирование кода.
Твоя задача — строго и скептически оценить, выполнены ли все критерии завершения цели.

[КОНТРАКТ ЦЕЛИ]: {{contract.objective}}
[КРИТЕРИИ ЗАВЕРШЕНИЯ]: {{contract.completion_criteria}}
[ФАКТИЧЕСКИЙ GIT DIFF]: {{workspace.git_diff_stat}}
[РЕЗУЛЬТАТЫ АВТОТЕСТОВ]: {{workspace.test_runner_output}}

Правила оценки:
1. Не верь текстовым заявлениям Исполнителя на слово — проверяй только фактический diff и вывод терминала.
2. Если Исполнитель удалил, закомментировал или поставил @skip на падающий тест ради зеленого билда — немедленно верни статус REGRESSED и укажи на саботаж тестов.
3. Верни ответ строго в формате JSON:
   {"status": "ACHIEVED" | "INCOMPLETE" | "REGRESSED", "missing_items": [...], "feedback_for_worker": "..."}
</evaluator_instructions>
```

## 5. Трехуровневая архитектура памяти и оптимизация кэша

При длительной работе (десятки итераций, сотни вызовов `bash` и `read_file`) контекстное окно быстро переполняется. Для сохранения скорости, точности и низкой стоимости применяется трехуровневая схема памяти:

### Уровень 1: Замороженное ядро (`Pinned System Prefix`)
* **Содержимое:** Системная инструкция + Карта репозитория (символьное дерево) + `Goal Contract`.
* **Правило:** Этот блок размещается в самом начале промпта и **никогда не изменяется** на протяжении всей жизни этапа.
* **Эффект:** Обеспечивает $100\%$ попадание в **Prompt Cache** (у OpenAI / Anthropic / Google), что снижает стоимость входных токенов на каждом следующем шаге цикла на $75\text{--}90\%$ и уменьшает задержку (TTFT).

### Уровень 2: Эпизодический журнал этапов (`Compacted Milestone Ledger`)
* **Содержимое:** Сжатая история уже закрытых этапов (`milestones` в статусе `verified`).
* **Правило:** Как только этап `ms_1` верифицирован Ревизором, Оркестратор **вырезает из истории чата** все $15\text{--}20$ промежуточных вызовов инструментов (чтение файлов, черновые правки, логи ошибок) и заменяет их одной записью в 4 строки:
  > `[MILESTONE ms_1 VERIFIED]: Создан интерфейс BillingService (services/billing.py). Схемы данных протестированы. Коммит-чекпоинт: refs/goals/ms_1.`

### Уровень 3: Активный верстак (`Sliding Working Scratchpad`)
* **Содержимое:** Полная несокращенная история вызовов инструментов, выводов терминала и диффов **только для текущего активного этапа**.

## 6. Защита от зацикливания (Anti-Thrashing & Oscillation Guard)

Автономные агенты склонны попадать в «беличье колесо»: исправляя ошибку $A$, они вызывают ошибку $B$, а чиня $B$ — возвращают ошибку $A$.

### Алгоритм детекции на уровне Оркестратора
1. **Нормализация и хэширование ошибок:**
   После каждого запуска команды в терминале (тесты, линтер, компилятор) с кодом возврата $\neq 0$, Оркестратор очищает вывод `stderr` от временных меток, путей к временным папкам и адресов памяти, после чего вычисляет хэш `SHA-256` (Error Fingerprint).
2. **Проверка триггеров зацикливания:**
   * **Триггер 1 (Прямой повтор):** Один и тот же `Error Fingerprint` появился $3$ хода подряд.
   * **Триггер 2 (Маятниковая осцилляция):** Хэши чередуются по схеме $H_1 \rightarrow H_2 \rightarrow H_1 \rightarrow H_2$.
   * **Триггер 3 (Локальное топтание):** Один и тот же файл редактируется $> 4$ раз внутри одного этапа без уменьшения общего числа падающих тестов.

## 7. Продвинутые инженерные идеи (Killer Features)

Ниже представлены архитектурные решения, которые выводят надежность системы Goal Engine на уровень промышленного продукта.

### Идея 1: Двухконтурная верификация (Zero-Token Fast Gate)
Не вызывайте LLM-Ревизора после каждого шага Исполнителя — это дорого и медленно.
* **Как внедрить:** Сначала запускается **Контур 1 (Детерминированный гейт)** — легкий скрипт на базе `Tree-sitter` (проверка синтаксиса измененных файлов за $15\text{ мс}$), быстрый линтер (`ruff` / `oxlint`) и таргетный тест измененного модуля.
* Если Контур 1 выявил синтаксическую ошибку или падение теста, Оркестратор **не вызывает LLM-Ревизора вообще**, а мгновенно возвращает трейсбек Исполнителю. LLM-Ревизор подключается только тогда, когда код технически чист и проходит все тесты.

### Идея 2: Теневые атомарные чекпоинты (Shadow Git Refs)
Если агент на 12-м шаге пошел по ложному пути и сломал архитектуру, просить его «откатить изменения вручную через редактирование файлов» — гарантированный путь к хаосу.
* **Как внедрить:** При каждом успешном прохождении этапа (`milestone verified`) Оркестратор в фоне выполняет команды низкоуровневого Git (`git write-tree` + `git update-ref refs/goals/<goal_id>/ms_<N>`), создавая невидимую точку сохранения без засорения основного `git log` и рабочей ветки пользователя.
* Если на следующем этапе срабатывает детектор зацикливания и агент заходит в тупик, Оркестратор программно откатывает состояние файлов к последнему чистому чекпоинту и передает агенту команду:
  > *«Подход через библиотеку X привел к неразрешимому конфликту зависимостей. Рабочее дерево автоматически откачено к чистому чекпоинту ms_1. Реализуй этап ms_2 альтернативным способом без использования библиотеки X».*

### Идея 3: Принудительная смена когнитивной роли (Root-Cause Role Pivot)
Когда агент $2\text{--}3$ раза подряд не может починить баг, он начинает хаотично менять строки наугад («метод тыка»).
* **Как внедрить:** При срабатывании триггера ошибки (2 неудачные попытки подряд) Оркестратор на **один ход** программно отключает у агента все инструменты записи (`write_file`, `apply_patch`) и оставляет только инструменты чтения (`read_file`, `grep`, `git_log`).
* Одновременно подменяется промпт хода на режим **Следователя (Root-Cause Investigator)**:
  > *«Инструменты редактирования временно заблокированы. Твои последние 2 правки не устранили причину ошибки. Изучи смежные файлы, проследи цепочку вызовов и сформулируй точную гипотезу первопричины бага. На следующем ходу инструменты записи будут разблокированы».*

### Идея 4: Бесшовное подруливание на лету (Non-Disruptive Hot Steering)
В стандартных UI, чтобы поправить работающего агента, пользователь вынужден нажимать кнопку «Stop», обрывая генерацию и ломая незавершенный шаг.
* **Как внедрить:** Во время активного цикла Goal поле ввода чата остается открытым с подписью *«Напишите уточнение — агент учтет его на следующем шаге без остановки»*.
* Сообщения пользователя попадают в буфер `steering_queue`. Оркестратор дожидается штатного завершения текущей атомарной операции (чтобы не повредить редактируемый файл) и вклеивает комментарий пользователя прямо в блок `[КОРРЕКТИРОВКА ОТ ПОЛЬЗОВАТЕЛЯ НА ЛЕТУ]` внутри `Continuation Prompt`.

### Идея 5: Динамическая маршрутизация моделей (Dynamic Model Tiering)
Использование самой тяжелой reasoning-модели на каждом из 30 шагов цикла сжигает бюджет впустую.
* **Как внедрить:** Оркестратор динамически меняет модель `Worker Agent` в зависимости от фазы и телеметрии:
  1. **Фаза планирования и декомпозиции (`ms_0`):** Флагманская модель с максимальной глубиной рассуждения.
  2. **Штатное выполнение шагов (`consecutive_identical_errors == 0`):** Быстрая и дешевая модель среднего класса (которая отлично пишет код по готовому плану).
  3. **Режим эскалации (`consecutive_identical_errors >= 1`):** Как только быстрая модель спотыкается на нетривиальном баге, Оркестратор автоматически переключает следующий ход на флагманскую модель для прохождения сложного участка, после чего снова снижает ранг. Экономия бюджета достигает $55\text{--}70\%$.

### Идея 6: Интерактивный «Компилятор цели» перед стартом (Dry-Run Spec Refiner)
90% провалов автономных агентов происходят из-за того, что пользователь задал размытую цель без измеримого критерия остановки (например: *«Оптимизируй запросы к БД»*).
* **Как внедрить:** Перед запуском длинного цикла вставьте быстрый 3-секундный шаг **Goal Compiler**. Легкая модель сканирует запрос и кодовую базу, предлагая пользователю карточку контракта на утверждение:
  * **Цель:** Устранить проблему $N+1$ запросов в эндпоинте `GET /api/orders`.
  * **Предлагаемый критерий завершения:** Автотест `pytest tests/perf/test_orders_query_count.py` проходит при лимите $\le 3$ SQL-запросов на вызов.
  * **Лимит бюджета:** до 15 шагов (~$0.40).
* Пользователь нажимает **«Подтвердить и запустить»**, и система стартует с формально проверяемым условием выхода.

## 8. Дорожная карта внедрения (Implementation Roadmap)

### Фаза 1: Базовый контур (MVP — 1–2 недели)
* Реализация JSON-схемы `GoalState` и таблиц хранения состояния в БД.
* Разработка `Loop Orchestrator` с 4 путями маршрутизации (`CONTINUE`, `ACHIEVED`, `BLOCKED`, `BUDGET_LIMIT`).
* Внедрение шаблонов `Continuation Prompt` и `Budget Limit Prompt`.
* Подключение базовых детерминированных проверок (запуск тест-раннера по завершении хода).

### Фаза 2: Контекст и надежность (Недели 3–4)
* Изоляция `Pinned System Prefix` для активации Prompt Caching.
* Сжатие завершенных этапов в `Compacted Milestone Ledger`.
* Внедрение `Evaluator / Judge` (отдельный вызов легкой LLM для семантической проверки диффов).
* Реализация `Anti-Thrashing Guard` (хэширование ошибок `stderr` и детектор зацикливания).

### Фаза 3: Продвинутое управление и UX (Недели 5–6)
* Внедрение теневых чекпоинтов `Shadow Git Refs` с авто-откатом при тупиковых ветках.
* Реализация механизма `Root-Cause Role Pivot` (временная блокировка записи при повторных багах).
* Добавление очереди `Non-Disruptive Hot Steering` и UI-индикатора прогресса по чекпоинтам.
* Внедрение `Dynamic Model Tiering` и предпускового `Spec Refiner`.
