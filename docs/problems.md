### 20.1 — Q9: как держать цены верными (сделано 2026-11-06)

Что нашлось:

- Цену через API отдаёт только OpenRouter (хаб уже берёт её из списка моделей). У Anthropic список моделей (`/v1/models`)
  отдаёт имя, окно контекста, предел ответа и возможности — без цен; у OpenAI, Gemini и DeepSeek цены только на
  страницах цен. Сверено 2026-11-06: цены Claude в хабе совпадают с опубликованными (Opus 5.5 — $4/$20, Sonnet 5.5 —
  $2/$10, Haiku 5.5 — $0,10/$0,50 до 100K токенов, Fable 5.1 — $10/$50).
- Цену у модели человек уже может поправить руками в «Модели» с датой (шаг 8.1).

Решение — таблица в программе остаётся, к ней три вещи:

- **Срок у цены.** У акционной цены — дата конца (`until`). GPT-5.6 Sol: $4/$20 «по крайней мере до 21 ноября 2026» (уточнено при работе: до 30 ноября)
  (`hub/gateway/openai_responses.py`). После даты цена в «Модели» помечена «акция кончилась — сверьте», оценки
  идут по ней с этой пометкой, пока человек не поправит (обычную цену берём со страницы OpenAI, когда делаем шаг).
- **Ступени длинного запроса** — общим полем таблицы цен, как `LONG_PROMPT` у OpenAI: Haiku 5.5 — дороже после 100K
  токенов ($0,50/$2,50), Pro-модели Gemini — после 200K; надбавка OpenRouter за длинный запрос
  (`pricing.overrides`) — в оценку каталога (точная сумма и так приходит в `usage.cost`).
- **Напоминание о свежести.** Цены старше 60 дней — пометка в «Модели» и строка в «Проверить систему» со ссылкой на
  страницу цен поставщика.
- **Принято:** праздники Китая у DeepSeek не учитываются — в праздник хаб считает по цене часа пик, то есть дороже,
  чем спишут; ошибка в безопасную сторону (так задуман и каталог, `hub/gateway/cloud_openai.py`).

### 20.2 — оценка запроса чата до отправки (D12; §5.4) (сделано 2026-11-06)

Что не так: цена до запуска оценивается только у задач агента (шаг 6.2); один запрос чата проверяется по уже
потраченному и может заметно перейти жёсткий предел. Решение: перед каждым запросом к платной модели хаб знает
размер запроса (подгонка `hub/fit.py` его уже считает) — верхняя оценка = вход × цена входа + предел ответа × цена
выхода; если она переходит остаток жёсткого предела — «спросить» или «стоп», как у бюджета сейчас. Тот же расчёт —
у шагов агента и ходов цели.

### 20.3 — Q9: лимиты подписки Claude Code (сделано 2026-11-06)

Что нашлось (справка Claude Code, 2026-11-06):

- Программа видит лимиты двумя путями. Первый — сообщение `rate_limit_event` в потоке `stream-json` (справка Agent SDK):
  состояние `allowed` / `allowed_warning` / `rejected`, время сброса, доля израсходованного (0–1) и окно (`five_hour`,
  `seven_day`, `seven_day_opus`, `seven_day_sonnet`, `overage`). Приходит, когда состояние меняется, — не на каждом
  запуске. Две справки SDK расходятся в написании полей (`resetsAt` и `resets_at`), а сырой вид строки CLI не описан.
- Второй — данные строки состояния (`statusline`): `rate_limits.five_hour` и `seven_day` с `used_percentage` (0–100) и
  `resets_at` — только у подписок Pro, Max и Ultra и только после первого ответа в сеансе. Работает ли строка
  состояния в `claude -p`, справка не говорит.
- Команды или поля, которые в `-p` отдают остаток подписки, нет: `/usage` — вид для человека, у `--output-format json` —
  только оценка цены.
- Хаб сейчас: `rate_limit_event` с состоянием не «allowed» уходит в ленту (`claude_code.limit`); остаток нигде не
  показан; цель, у которой Claude Code упёрся в лимит, получает ошибку хода.

Решение:

- Хаб читает оба написания полей и помнит последнее состояние каждого окна (доля, сброс) — в строке состояния окна и в
  выборе модели: «Claude Code: 5 часов — 85 %, сброс в 15:45».
- `allowed_warning` — предупреждение в чате; `rejected` — цель и экзамен не падают, а встают на паузу «лимит подписки до
  15:45» с уведомлением (Windows, Telegram); продолжает человек.
- Строка состояния: проверить на настоящем CLI (этап 28), запускается ли она в `-p`. Если да — хаб подключает к своим
  запускам свою команду строки состояния (через `--settings`), которая передаёт ему `rate_limits`: тогда проценты видны
  и до первого предупреждения. Если нет — только `rate_limit_event`.
- Сырой вид `rate_limit_event` снять одной строкой с настоящего CLI (этап 28) и записать в тест заменителя
  `tests/fake_claude.py`.

### 20.5 — Claude Code на экзамене полигона (сделано 2026-11-06)

Что не так: `hub/proving.py:281` отказывает Claude Code с устаревшей причиной «цель его пока не ведёт (этап 11.7)» — этап

### 20.6 — Q16: подпись кода

Подготовлено 2026-11-06 по слову пользователя: сборка выпуска на GitHub Actions (`.github/workflows/release.yml`), «Code signing policy» в README, `PRIVACY.md`, название и версия продукта в установщике. Заявку пользователь подал 2026-11-06 (`signpath.org/apply`: «Form submitted»); ждём ответа фонда. Подпись в сборке — когда фонд примет проект; откажет — Certum (ниже).

Что нашлось (официальные страницы, сверено 2026-11-06):

- **SignPath Foundation** — бесплатно для открытого кода; GPL-3.0-or-later подходит. Сертификат выдан на SignPath
  Foundation (уровень OV), имени AFO в нём нет. Условия:
  - сборка из исходников на GitHub Actions (машины GitHub), их действие подписи;
  - каждый выпуск подтверждается вручную;
  - двухфакторный вход на GitHub и SignPath;
  - на странице проекта — «Code signing policy» и заявление о приватности.

  Порог известности не опубликован: молодому проекту могут отказать «нет широкой известности» (такой случай есть,
  2026-10). Условия помечены «черновик».
- **Microsoft Artifact Signing** (бывший Trusted Signing, ~$9,99 в месяц) — частным разработчикам только из США и Канады,
  с проверкой документа и лица: прежний выбор Q16 («облачная подпись Microsoft») для частного лица вне этих стран
  закрыт.
- **Обычный сертификат частного лица:**
  - Certum Open Source Code Signing в облаке — от €49 в год, в сертификате — настоящее имя («Open Source Developer …»);
  - SSL.com — $129 в год и ещё токен или облако.

  С 2023 года ключ — только на токене или в облачном HSM; с 2026-03-01 сертификат живёт не дольше 460 дней.
- **EV-сертификат** SmartScreen больше не обходит (Microsoft, с 2024 года) — переплата.
- **Microsoft Store** бесплатен частным разработчикам с 2025-09, но без предупреждения SmartScreen проходит только MSIX, а
  его Q16 отверг (перенаправляет запись в реестр и AppData).
- С любой подписью SmartScreen сначала всё равно предупреждает. Доверие копится неделями и сотнями чистых установок, а
  смена сертификата начинает его заново.

Решение:

- **Сейчас, без счетов и заявок — сборка выпуска на GitHub Actions.**
  - Машина Windows от GitHub собирает по метке `vX.Y.Z` то же, что сейчас `python -m installer.build` локально:
    встраиваемый Python с проверкой sha256, библиотеки из `requirements.lock`, Inno Setup (`installer/afo.iss`).
  - Выпуск — с её файлами, `.sha256` — после подписи.
  - Это нужно SignPath и делает выпуски воспроизводимыми. Локальная сборка остаётся для проверки.
- **Подписывать только своё:** установщик, деинсталлятор (Inno `SignedUninstaller`: подписанная копия один раз) и свои
  `.exe`. Файлы python.org уже подписаны Python Software Foundation — их не трогать. Каждая подпись — с меткой времени.
- **Когда программа пойдёт другим людям** (как и было в Q16) — заявка в SignPath Foundation. Её подаёт пользователь: его
  учётная запись и двухфакторный вход. В README — раздел «Code signing policy» с их словами.
- **Если SignPath откажет** — Certum Open Source в облаке (~€49 в год, в сертификате — имя пользователя). До оплаты
  спросить Certum, принимают ли документы страны пользователя; подпись на GitHub Actions — с секретом в окружении,
  которое требует подтверждения пользователя.
- **Не берём:** Microsoft Artifact Signing (частным лицам вне США и Канады закрыт), EV (переплата), MSIX и Store (Q16).
- Шаги: **20.6а** — сборка на GitHub Actions (код, без подписи); **20.6б** — подпись, по слову пользователя и после
  ответа SignPath или Certum.

## Этап 21 — Claude Code исполнителем цели — сделан 2026-11-06

- 21.1 (сделано 2026-11-06) — защита от хождения по кругу не видит правок Claude Code: третий сигнал (один файл правится раз за разом)
  считает записи хаба, а Claude Code пишет сам; то же — файлы, которые пишут команды. Решение: в начале хода — снимок
  дерева, как у точек сохранения 11.6 (`GIT_INDEX_FILE`, `write-tree`), в конце — список изменённых файлов по разнице
  деревьев. Один путь для всех исполнителей; свои записи хаба считать отдельно больше не нужно.
- 21.2 (сделано 2026-11-06) — `--effort` не передаётся: глубина чата Claude Code не доходит. По справке: уровни `low`, `medium`, `high`, `xhigh`,
  `max` (Fable 5.x, Opus и Sonnet 5.x, Haiku 5.5, Opus 4.7–4.8; у Opus и Sonnet 4.6 нет `xhigh`); уровень, которого
  модель не знает, CLI сам опускает до ближайшего меньшего; переменная `CLAUDE_CODE_EFFORT_LEVEL` сильнее флага.
  Решение: глубина чата → `--effort` (кроме «авто» — тогда флага нет); у моделей, которых нет в списке справки (Haiku 4.5
  и старше), — без флага; переменная `CLAUDE_CODE_EFFORT_LEVEL` из окружения запуска убирается, когда хаб передаёт
  флаг, — иначе выбор в окне молча не действовал бы.
- 21.3 (сделано 2026-11-06) — сообщения подагентов Claude Code не попадают в чат (§5.4). По справке они уже идут в потоке `stream-json`:
  `assistant` и `user` с `parent_tool_use_id` — id вызова, который запустил подагента (у главной беседы — `null`); по
  умолчанию — только вызовы инструментов и их результаты, текст и размышления — с флагом `--forward-subagent-text`
  (CLI 2.1.211+). Решение: хаб собирает такие сообщения под вызовом, который запустил подагента, — в окне
  сворачиваемым блоком «подагент: …» с его вызовами; флаг — когда версия CLI его знает (`claude --version`). В
  историю беседы они идут как часть хода, модель главной беседы их не получает (у неё — только итог подагента, как
  сейчас).

## Этап 23 — надёжность и диагностика — сделан 2026-11-06

- 23.1 (сделано 2026-11-06) — журнал Telegram пишет только текст ошибки (`hub/telegram.py:193`); у обрыва связи он пустой. В установленной
  AFO — 29 записей «telegram: ; again in 2 s» за 4–6 ноября, в основном ночью (вероятно, сон компьютера): причину не
  понять. Решение: вид ошибки и текст; одинаковые подряд — одной строкой «ещё N раз».
- 23.2 (сделано 2026-11-06) — `data/logs/app-crash.log` копии разработки, 29.10: «Windows fatal exception 0x800706be» (сбой удалённого
  вызова COM) в главном потоке окна, не разобран. faulthandler на Windows пишет и перехваченные исключения COM, поэтому
  запись — не доказательство вылета. Решение: окно и хаб отмечают штатный выход; при следующем запуске запись из
  сеанса, который кончился штатно, помечается «перехваченное исключение Windows, не вылет», настоящий вылет —
  строкой в «Проверить систему».
- 23.3 (сделано 2026-11-06) — хаб, запущенный переходником stdio, умирает вместе с клиентом MCP на Python SDK: клиент держит переходник в
  задании Windows без права выхода (§5.4). Решение: если выйти из задания нельзя, переходник запускает хаб через WMI
  (`Win32_Process.Create`) — такой процесс рождается вне задания клиента. Тест — задание без права выхода (`ctypes`).
- 23.4 (сделано 2026-11-06) — порт 8080 занят моделью Strata: llama-swap не поднимается, хаб видит только «не отвечает» (§5.4). Решение:
  хаб узнаёт по сканеру процессов, кто держит порт, и пишет «порт 8080 занят: strata.exe (pid …) — закройте модель
  Strata» в строке состояния и в «Проверить систему».
- 23.5 (сделано 2026-11-06: **принято** — новее 0.26.0 версии нет, на 0.26.0 и Python 3.14.7 сбой не воспроизвёлся, обход оставлен) — tree-sitter 0.26 под Python 3.14 иногда роняет процесс на `Node.start_point` / `Node.text`; индекс обходит
  их (§5.4). Решение: проверить новую версию на тех же случаях; если сбоя нет — убрать обход, иначе — **принято** до
  следующей версии.
